一、最终裁定
Phase 0 不是完整商业 App，但用户第一眼必须像正式产品。
不接受默认 Gradio / Streamlit 风格作为用户第一眼界面。
Next.js 负责用户可见的高颜值工作台；Python / Gradio / Streamlit 负责内部调试和技术验证。
先打通“整页解析 → 题目列表 → 单题辅导 → 视觉追问”主链路，其他业务功能只做入口、占位或本地 Mock。
视觉策略要高级，但工程实现必须克制，避免动画、bbox、登录、支付、状态流等前端黑洞。
本版新增裁定：前端必须预留云端 API、用户权益、学豆余额、激活码核销、本地缓存删除和正式支付占位，但 Phase 0 不接真实支付 SDK、不做真实激活码核销。
二、产品定位与设计语言
产品定位：家庭学习工作台，而不是单纯拍照搜题 App。
核心情绪价值：效率、秩序、缓解焦虑、可信、温和、有陪伴感。
目标用户：家长与孩子。家长更关注可信、省心、可控；孩子更关注清晰、不压迫、愿意继续看。
第一眼视觉必须降低“作业辅导焦虑”，让用户感到“这件事被整理好了”。
商业化提示必须克制，不能把产品第一眼做成收款页。权益、额度、激活码只作为状态和入口，不抢主链路。
三、双层架构与云端预留裁定
注意：使用 Next.js 不等于 Phase 0 要提前开发完整业务系统。Next.js 只是高颜值用户可见壳和主链路承载层；云端数据库、对象存储、支付订单和学豆体系必须预留接口，但不得拖慢 Phase 0 主链路。

五、前端技术栈裁定
不采用 Ant Design / MUI / 从零手写组件。Ant Design 与 MUI 偏企业后台风，不适合“温和家庭教育产品”的气质。
Next.js App Router 边界：Phase 0 主链路页面默认使用 "use client" Client Components。上传、轮询、bbox 高亮、对话输入、假打字机、视觉二次路由均属于客户端强交互，不在 Phase 0 强行拆 Server Components；Phase 1 再按需优化 Server / Client 边界。
六、API Contract 与商业化预留接口
Phase 0 API Contract 必须在开工前锁定，避免前后端各自发明接口。商业化接口只做类型、状态和 Mock 占位，不接真实支付。
6.0 请求身份标识与最小认证占位
Phase 0 typed fetch client 必须统一在请求 Header 中携带 X-Child-Id: demo_child_001；本字段用于 Mock 和联调阶段区分孩子数据，不能散落在组件中手写。
Phase 0 如需区分家长账号，可同步携带 X-Demo-User-Id: demo_parent_001；后端仅作测试隔离，不作为正式鉴权。
/api/me/entitlement、/api/questions/{question_id}/tutor、/api/questions/{question_id}/vision、/api/questions/{question_id}/status 均必须能读取该身份占位，否则无法判断权益、额度和缓存归属。

type EntitlementStatus =

AI 调用按钮的可用、降级、拦截和提示必须依赖 entitlement 状态，不得在组件里写死“永久免费”“无限次使用”“无限识别”。
6.3 API 统一错误响应格式
FastAPI 后端不得直接把默认 detail、traceback、Pydantic 校验栈暴露给前端。typed fetch client 只解析统一包裹格式：
// success
{ "ok": true, "data": { ... }, "request_id": "req_xxx" }

// error
{
  "ok": false,
  "code": "ocr_failed",
  "message": "图片可能太模糊，识别失败，请重新拍摄或上传。",
  "request_id": "req_xxx",
  "details": null
}
typed fetch client 统一读取 code 做错误分类，读取 message 做用户可见提示；组件不得各自猜测 response.detail / error.message。
FastAPI 默认 422 / 500 / timeout 必须由全局 exception handler 转换为统一格式。
前端错误态只展示 message，不展示 traceback、字段栈、Pydantic 原始报错。
七、解析状态通信方案
Phase 0 采用前端轮询 polling；Phase 1 可升级 SSE；不使用 WebSocket。
POST /api/parse-jobs          # 创建解析任务
御三家异步裁定：POST /api/parse-jobs 必须立即返回 job_id。Phase 0 后端使用 FastAPI BackgroundTasks 或 asyncio.create_task 异步执行解析链路；Phase 1 替换为 ARQ / Dramatiq / Redis Queue，不改变前端接口形状。前端不得同步等待整页解析完成。
GET  /api/parse-jobs/{job_id} # 每 1.5 秒轮询任务状态
0-40 秒：正常显示阶段进度。
40-60 秒：提示“这页题目较复杂，正在继续处理”。
超过 60 秒：显示“处理时间较长，可以稍后重试”。
completed / failed：停止轮询。
轮询状态应携带 task_id / job_id，便于后续云端任务与 Redis 队列升级。
拿到 job_id 的瞬间，必须立刻写入 URL 路由参数，例如 /workspace?job_id=xxx；组件初始化时优先从 URL 恢复轮询进度，避免刷新或切后台导致任务丢失。
7.1 解析状态页设计与动效降级
解析状态页目标不是炫技，而是让家长知道系统没有卡死。状态动效使用“知觉欺骗”：看起来在扫描、处理、校验，但不与后端真实坐标或真实 OCR 进度做像素级同步。
顶部必须给出时长预期：“通常需要 20-30 秒，请保持页面打开”。
禁止按真实 OCR 坐标逐字浮现。
禁止按真实增强区域做局部动画。
禁止与后端进度做逐帧同步。
八、页面设计规范
8.1 登录 / 入口页
做漂亮入口页，但不做完整账号系统。保留 Logo、Slogan、手机号/邮箱样式、激活码输入框和“进入学习工作台”按钮。
8.2 首页：家庭学习工作台
让家长一进来就知道今天要处理什么作业、从哪里上传、解析进度如何、孩子有哪些待学习题。
8.3 上传 / 导入页
降低家长焦虑，明确告诉用户系统会自动增强清晰度并整理成待学习清单。
PDF 预览采用降级方案：Phase 0 不引入 PDF.js。上传后先显示文件名与页数占位卡片；等后端返回 enhanced_image_url 或页面渲染图后，再替换为图片预览。
PDF 多页裁定：Phase 0 只处理 PDF 第 1 页。上传后明确展示“当前将处理第 1 页，更多页选择将在后续版本开放”。
Phase 0 /api/parse-jobs 可携带 page_range=1 作为 multipart 表单字段；如前端未传，后端默认处理第 1 页。Phase 1 再支持 1,3-5 等页码选择。
Phase 0 上传页不得开发复杂 PDF 页码选择器、缩略图分页器或 PDF.js 预览器，避免拖慢主链路。
图片上传前必须做客户端压缩：使用 Canvas API 将长边压缩到 ≤2200px，JPEG 质量约 0.85，目标文件大小 ≤3MB。PDF 不做前端压缩，直接上传原文件。上传协议必须使用 multipart/form-data，禁止把图片转 Base64 放入 JSON。
8.4 题目列表页
上半屏展示增强图和 bbox，下半屏展示题目列表。移动端优先使用上下结构，桌面端可扩展为左右结构。
8.5 单题辅导页
这是产品核心场景。顶部展示裁切图或过期占位，中间是 AI 辅导对话流，底部是状态按钮和输入框。
8.6 权益 / 学豆 / 激活码状态位
前端必须支持会员、AI 能量、激活码入口和支付占位状态，但 Phase 0 不做真实支付。
8.7 本地错题缓存与家长删除入口
错题可以保存在手机本地，但不能设计成“只存在本地”。正式多用户阶段应采用云端主账本 + 手机本地加密缓存。
前端必须预留“删除本地缓存”“删除某次作业”“删除孩子全部学习资料”三个入口或状态。
学习数据、图片缓存、错题记录支持家长删除；支付订单、充值流水和额度流水按财务与风控要求保留必要记录。
PWA 本地缓存可能被浏览器清理，因此不能作为唯一数据源。
PWA 每次启动时必须校验本地数据版本与云端 parse-jobs / assignments / mistake-book 列表是否一致；不一致时静默拉取，避免 iOS Safari 清理 IndexedDB 后用户误以为数据丢失。
8.8 Service Worker 与 IndexedDB 职责边界
Service Worker + Cache Storage 只负责静态资源、PWA 外壳资源，以及可重新拉取的图片/增强图 URL 缓存；不得把错题、解析、对话等业务数据塞进 Service Worker 缓存。
IndexedDB 负责结构化业务数据：question_text、visual_description、structured_conditions、AI 解析全文、错因、知识点、状态标记、同步版本号。
二进制大文件不长期进入 IndexedDB；原图、增强图、裁切图只做短期 URL/Cache Storage 缓存，并支持家长删除。
云端主账本是账号、作业、错题、权益和支付记录的最终依据；PWA 本地缓存只做体验增强和短时离线。
九、bbox 渲染与坐标映射方案
Phase 0 使用 <img> + 绝对定位 div 覆盖 bbox；不用 Canvas；只做单向联动。
后端返回的 bbox 坐标是原图坐标系，前端展示图片会缩放，必须做坐标映射。
前端必须同时拿到 original_width、original_height、display_width、display_height。
bbox 渲染层覆盖在图片容器上，使用 position:absolute。
display_x = bbox_x × display_width  / original_width
display_y = bbox_y × display_height / original_height
display_w = bbox_w × display_width  / original_width
display_h = bbox_h × display_height / original_height
容器或窗口尺寸变化时必须重新计算 bbox 显示坐标；建议使用 ResizeObserver 监听图片容器变化，不依赖 window.resize。
bbox 渲染必须等待图片 onLoad 完成后再计算坐标。原图尺寸使用 img.naturalWidth / img.naturalHeight，显示尺寸使用 img.clientWidth / img.clientHeight。
图片未加载完成前不得渲染 bbox，避免所有框堆叠在左上角。
十、DeepSeek 辅导输出方案
Phase 0 使用假打字机；Phase 1 再升级真流式 SSE。
Phase 0：后端一次性返回完整解析，前端用 setInterval 或 requestAnimationFrame 模拟逐字输出。
假打字机速度控制在 40-50 字/秒。点击对话内容区域或“跳过动画”按钮后，立即展示完整文本，避免孩子每次等待动画播完才能继续追问。
不要默认直接给完整答案，应按“提示 → 分步讲解 → 完整解析 + 易错点”三层呈现。
对话区必须避免大段文字压迫，重点条件、公式、结论应卡片化。
DeepSeek 或视觉模型调用前，前端要尊重 entitlement 状态；额度不足不得继续触发高成本深度调用。
扣费展示必须以后端成功返回完整解析为准：/tutor 成功后立即写入 IndexedDB 缓存，再更新 entitlementStore 的展示余额。若用户刷新或退出，页面应从缓存恢复已扣费的完整解析，避免“豆子扣了但内容丢失”。
十一、视觉二次路由交互
当孩子追问图、线段、表格、箭头、阴影、坐标等视觉问题时，触发视觉重读。
前端出现状态气泡：“AI 正在仔细观察原图...”。
顶部题图覆盖雷达扫描或放大镜游走动效，用于掩盖 Vision 模型高延迟。
优先复用已有 visual_description；只有描述不足时再调用视觉模型。
视觉二次路由不能每次无脑调用模型，必须服务真实视觉追问。
Phase 0 视觉二次路由由前端关键词规则触发，不由后端模型判断。命中“图、图中、线段、表格、几何、箭头、阴影、方格、坐标、这条、这个图”等关键词时，前端先展示等待动画，再调用 /api/questions/{id}/vision。
视觉二次路由属于高成本调用，必须接入权益/额度状态位；不得绕过 AI 成本日志预留。
11.1 /vision 扣费与结果恢复机制
/vision 与 /tutor 同属高成本调用，必须使用相同的“成功后缓存、再更新余额展示”原则。
/vision 成功返回后，前端先将 visual_description 补充内容、answer、usage、credit_cost、billing_status 写入 IndexedDB；建议 key 为 question_id + vision_call_id 或 question_id + timestamp。
用户在视觉重读动画播放中刷新、切后台或退出页面时，重新进入单题页必须能从 IndexedDB 恢复最近一次视觉重读结果，不重复扣费。
若后端返回 cached_result_id，前端恢复时优先使用 cached_result_id 与 question_id 绑定，不依赖 Zustand 临时状态。
视觉重读完成后再同步刷新 entitlement 查询，并由 entitlementStore 展示最新余额。
十二、移动端优先策略
Phase 0 优先适配 375px-430px 手机视口，桌面端作为扩展适配。
家长核心使用场景是手机拍整页作业，因此移动端体验是第一优先级。
优先验证：手机上传图片、调用相册/相机、查看 bbox 是否可读、单题辅导是否顺手。
底部输入框必须处理软键盘遮挡问题。
软键盘方案：iOS Safari 使用 window.visualViewport 监听高度变化，动态调整输入区 bottom；Android Chrome 使用 100dvh 替代 100vh，并配合 env(safe-area-inset-bottom) 处理安全区。
移动端题图与题目列表优先上下结构，避免左右栏过窄。
PWA 作为早期移动端策略时，本地缓存只能作为体验增强，不能当作唯一数据源。
十三、设计 Token 与视觉规范
不能只写“奶油白、护眼青”，必须写成可执行 Token。Token 第一版先固定，后续根据真实用户反馈再微调。
十四、Typography 可读性规范
不建议所有英文和数字都用等宽字体。只有代码、JSON、日志使用 monospace；公式用专门公式渲染。
公式渲染裁定：小学/初中数学复杂度下唯一采用 KaTeX + react-katex。
原因：KaTeX 包体更小、渲染更快、React 集成更简单；Phase 0/1 不引入其他公式渲染库。

    workflowStore.ts   # 选中题、bbox 高亮、UI 流程状态

15.1 entitlement 单向数据流裁定
推荐最小数据流：
useEntitlementQuery()
  -> onSuccess(normalizeEntitlement)
  -> entitlementStore.setState(...)
  -> components read entitlementStore only

/tutor or /vision success
  -> write IndexedDB result
  -> update display balance from response
  -> queryClient.invalidateQueries(["entitlement"])
TanStack Query 是权益数据的唯一远程数据源，负责请求 /api/me/entitlement、失败重试、失效刷新和缓存同步。
entitlementStore 只负责把最新权益状态转成 UI 可读状态，供按钮、徽章、提示条、拦截弹层读取；不得自行伪造云端余额。
数据流必须单向：TanStack Query onSuccess → normalizeEntitlement() → setEntitlementStore() → 组件读取 entitlementStore。
高成本调用 /tutor 或 /vision 成功后，前端可先根据响应中的 credit_cost 做本地展示同步，但必须随后 invalidate/refetch /api/me/entitlement。
组件不得一部分读 TanStack Query、一部分读 entitlementStore 来决定按钮可用性，避免“余额够但按钮灰”或“余额空仍可点”的冲突。
十六、错误状态 UI 方案
真实样本一定会失败，错误态必须提前设计。用户不能看到技术错误栈。
禁止暴露：schema error、json parse failed、500 internal server error、traceback。
错误提示必须给用户一个下一步动作，而不是只说失败。
支付、额度、激活码相关错误不得使用“系统异常”笼统提示，必须区分“未开通、额度不足、激活码无效、网络失败”。

API Contract 追加硬规则
/api/parse-jobs 请求 Content-Type 必须为 multipart/form-data，由浏览器自动生成 boundary；前端不得手写错误的 Content-Type。

client_task_id 定义：前端在用户确认上传前生成 UUIDv4，并随 /api/parse-jobs 提交；后端以 child_id + client_task_id 做幂等键，防止用户连点、刷新重传或网络重试创建重复解析任务。若后端发现重复 key，应返回已有 job_id。
统一错误格式是联调硬要求：所有失败响应必须为 { ok:false, code, message, request_id, details }，前端 typed fetch client 只消费该格式。
后端返回 job_id 后，前端必须同步写入 URL 和 TanStack Query 缓存。
所有高成本模型接口必须返回 usage / credit_cost / billing_status / cached_result_id 等字段占位，便于后续真实计费。
所有本地缓存恢复必须以 remote_id、job_id、question_id 为主键，不以页面临时状态为准。
