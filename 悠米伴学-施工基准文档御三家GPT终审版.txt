0. GPT终审修订意见
原施工基准的核心模型链路继续保留：OCR 认字，OpenCV/OCR block/版面规则切物理块，视觉模型理解图形与版面，DeepSeek 负责讲题辅导。
本版与《悠米伴学-前端工程v1.1-GPT终审版》对齐：Next.js 是用户可见工作台，Gradio/Streamlit 仅作为内部调试层；前端 API、Header、multipart 上传、job_id URL 恢复、CORS、Hydration、防刷新、PWA 缓存边界均纳入总基准。
本轮终审补丁全部纳入：学豆与会员归属、图片过期时间戳、retry_count、reason_code、needs_review 使用路径、对话摘要/截断、迁移策略、Secrets 管理、激活码限流、加密支付回调、model_call_log 字段统一、question_attempt 字段、chat sequence_number、后端对话上限、next_review_at、样本分布、索引策略。
本次成本扩容整合补丁纳入：所有模型 API Key 禁止进入前端/客户端；统一通过后端 AI Gateway 调用模型；Phase 1 起采用队列 + Worker Pool 处理并发；固定成本按用户规模分阶段升级，不按 500 人并发提前采购；错题库以结构化数据入库、图片/PDF 入对象存储并设置生命周期；云端主账本与手机本地缓存边界继续保留。
御三家定稿补丁纳入：Phase 0/1 不新增 /chat 接口，统一用 /tutor 承担首次辅导与追问；ai_tutoring_chat 跟随错题生命周期；parse-jobs 使用 BackgroundTasks/异步执行立即返回 job_id；AI Gateway 按错误类型分流重试；activation_codes 使用 used_by_parent_user_id；mistake_book_item 使用 error_type_code + reason_desc。
本版仍是 Phase 0/1 开工基准，不是完整商业 App、完整支付系统或完整移动端 App 的一次性建设方案。
1. 产品定位与总目标
悠米伴学不是普通拍照搜题 App，而是面向家庭场景的学习工作台：把整页作业、PDF、微信截图等输入，整理成可点击的题目清单、单题 AI 辅导、错题沉淀、孩子学习状态与下一步目标。

4. 总体技术架构

统一架构裁定：家长端、PWA、App 不得直接接触 Qwen-VL、OCR、DeepSeek 等模型供应商 API Key。所有模型调用必须进入 FastAPI 后端的 AI Gateway，由后端完成身份校验、权益检查、限流、排队、模型调用、model_call_log 记录和 credit_ledger 扣减。
建议逻辑链路：家长端/PWA → typed fetch client → FastAPI API 层 → QueueAdapter → AI Worker/ModelProvider → PostgreSQL/R2/model_call_log/credit_ledger。前端只拿 job_id、状态和结果，不直接调用模型。
5. 数据库、服务器与云端资源策略
最终产品需要云端数据库、对象存储和后端 API，但 Phase 0 不建议一开始租传统云服务器或自建数据库。先用轻量云服务与本地开发跑通验证，避免把精力消耗在运维、备份、安全组、HTTPS、数据库维护上。


5.1 低固定成本启动原则
变动成本主要来自模型 API，可通过会员额度、学豆、降级模型和限流控制；初期真正要压低的是没人用也会产生的固定成本，包括云服务器、托管数据库、Redis 实例和常驻 Worker。
Phase 0/1 不按 500 人生产并发提前采购固定资源。优先使用静态托管、Supabase Free/Pro、Cloudflare R2/OSS、Upstash Redis 按量、低配 FastAPI 服务和 1 个 Worker。未达到稳定付费用户前，不自建高配 ECS/PostgreSQL/Redis。
推荐成本阶段：0-50 个内测用户固定成本目标 0-100 元/月；50-200 个真实用户固定成本目标 100-600 元/月；500 个高频用户再升级到托管数据库、Redis 队列、1-3 个 Worker 和对象存储生命周期管理，固定成本约 600-2000 元/月，模型 API 成本另计。
5.2 可扩容代码架构原则
不是“用户多了再大改代码”，而是“代码架构现在一次写对，云资源按用户量逐步加钱”。从第一版开始必须抽象 Repository、StorageAdapter、QueueAdapter、ModelProvider/AI Gateway，避免业务代码写死 SQLite、本地文件、同步模型调用或单一供应商。
Phase 0 可以用本地/轻量实现：SQLite 兼容 PostgreSQL 语法、本地文件或 R2、小队列/Upstash、单 Worker；Phase 1/2 通过配置切换为 PostgreSQL、R2/OSS、Redis/Upstash、多个 Worker，不推翻前端 API 和业务流程。
5.3 500 用户并发处理裁定
500 个家长同时使用时，后端不得让请求同步直冲模型。/api/parse-jobs 必须保存文件、写 parse_job、入队并立即返回 job_id；前端通过轮询或后续 SSE 获取状态。真正打到模型供应商的并发由 Worker 数量和 Provider 限流控制。
高峰期允许队列变长，但不允许系统崩溃、重复扣费或 API 成本失控。必须有队列长度、平均等待时间、失败率、重试次数、单用户调用量和模型费用监控。
5.4 错题库容量与存储分层
低成本数据库可以承载初期错题库，但前提是数据库只存结构化错题数据、知识点、错因、掌握度、对话摘要、支付流水和成本日志；原图、增强图、PDF 页面图、裁切图不得长期塞进 PostgreSQL。
图片/PDF 必须进入对象存储 R2/OSS，并设置默认 7 天生命周期与家长提前删除能力。错题长期展示依赖 question_text、visual_description、structured_conditions、mistake_reason、knowledge_points、redo_status，不依赖临时图片 URL。
500 高频用户场景下，Supabase Free 只能用于 Demo/内测，不能承载长期高频错题库。随着用户增长，应升级 Supabase Pro、增加数据库空间或迁移独立 PostgreSQL。model_call_log 和原始模型 JSON 可做 30-90 天热数据保留与归档；ai_tutoring_chat 属于错题学习资产，跟随 mistake_book_item 生命周期，家长删除错题/孩子资料时再删除，不按普通运营日志时间窗清理。
6. 账号、孩子身份与鉴权占位
所有和作业、权益、学豆、错题、AI 调用相关的接口，都必须能识别“哪个家长/哪个孩子”。Phase 0 可使用 Header 占位，Phase 1 升级为 JWT。

Phase 0 typedFetch headers:

X-Demo-User-Id: demo_parent_001

Phase 1 typedFetch headers:
Authorization: Bearer ***
7. API Contract 与联调协议
API Contract 必须先于前后端开工锁定。所有前端业务组件必须通过 typed fetch client 调用接口，不允许散落 fetch。FastAPI 必须提前配置 CORSMiddleware 和统一错误格式。

统一响应格式：
成功：{ "ok": true, "data": { ... }, "request_id": "req_xxx" }
失败：{ "ok": false, "code": "ocr_failed", "message": "用户可见提示", "request_id": "req_xxx" }
追问接口裁定：Phase 0/1 不新增 /chat 接口。所有首次辅导与后续追问统一走 POST /api/questions/{question_id}/tutor，请求体使用 mode: initial | followup 区分；前端只传增量 message，后端负责读取 ai_tutoring_chat 上下文、校验轮数、生成结果并写入 sequence_number。
8. 上传、PDF、幂等与状态恢复
图片上传前由前端 Canvas 压缩：长边建议不超过 2200px，大小不超过 3MB；PDF 不由前端压缩。
禁止 Base64 JSON 上传图片。/api/parse-jobs 必须使用 multipart/form-data 上传原文件或压缩后的 Blob。
Phase 0 PDF 只处理第 1 页；但后端必须先用 PyMuPDF 判断文字型 / 扫描型 / 混合型，不能简单全部当图片处理。
client_task_id 由前端生成 UUID，用于幂等防重。后端应在同一 child_id 下防止用户连点创建重复任务。
拿到 job_id 后，前端必须立即写入 URL，例如 /workspace?job_id=xxx；组件初始化时优先从 URL 恢复轮询。
读取 IndexedDB / LocalStorage 的逻辑必须放在 useEffect 挂载后执行，避免 Next.js Hydration Mismatch。
Phase 0 图像增强只做方向纠正、尺寸规范化、必要灰度/对比度增强；不做去阴影、去反光、复杂超分。

9. 模型分工、Provider 与成本日志



模型供应商 API Key 只允许保存在服务端环境变量或云 Secret Manager，不得写入前端仓库、移动端包、PWA 静态资源或用户可见配置。家长不需要、也不应该提供自己的 API Key。
AI Gateway 必须在模型调用前执行 entitlement/credit 检查、单用户限流、全局队列限流和幂等校验；模型调用成功后统一写 model_call_log，再按规则写 credit_ledger。失败、超时、重试和降级必须可追踪。
模型重试裁定：AI Gateway 必须按失败类型分流。Schema 校验失败时携带上一次校验错误重试并可调整 Prompt，最多 2 次；Provider 网络超时使用指数退避，最多 3 次，不换 Prompt；Provider 429/rate_limit 禁止立即重试，应写入队列延后处理，避免触发更严限流或封禁。
10. 会员、激活码、学豆与支付结算预留
商业化底层要提前预留，但 Phase 0 不能变成支付系统。当前最小闭环是：前端展示权益状态和激活码入口，后端保留 activation_codes、credit_ledger、model_call_log 的接口和表结构；真实支付 SDK 延后。



11. 本地缓存、错题保存与家长删除
错题可以保存在手机本地，但不能把本地缓存当作唯一数据源。正式产品以云端主账本为准，手机本地作为离线体验和隐私友好的缓存层。

Service Worker 只缓存静态资源和可再获取的图片 URL，不缓存错题正文、对话、学豆余额等业务真相。
IndexedDB 负责结构化业务缓存：question_text、visual_description、tutor_result、vision_retry_result、local_cache_version。
PWA 本地缓存不可靠，iOS 可能清理长期未使用站点数据；每次打开 App 必须校验本地版本与云端 parse-jobs/questions 列表。
家长删除入口至少包括：删除本地缓存、删除某次作业、只删除图片、删除某个孩子全部学习资料。
错题库采用“云端主账本 + 手机本地缓存”。手机本地可以缓存错题列表、题目文本、解析全文、最近对话和少量图片缓存，但不能作为唯一数据源；换手机、清缓存、PWA 被系统清理后，必须能从云端恢复。
家长删除学习数据时，必须同时触发本地缓存清理与云端删除/软删除流程。支付订单、充值流水、学豆流水、风控日志按财务与争议处理要求保留必要记录，不纳入一键物理删除承诺。

13. 解析任务状态机与异步执行
任务状态必须与前端解析状态动画对齐。前端动画可以做知觉欺骗，但状态字段必须真实、可轮询、可恢复。


异步队列是 Phase 1 并发能力的边界，不是可选优化。即使 Phase 0 采用本地单进程，也必须保留 enqueue_parse_job / worker_process_job / save_result 的函数边界，禁止把上传、模型调用、写库和返回结果写成一个同步长请求。
Worker 并发数量按资源配置逐步增加：初期 1 个 Worker 允许排队；中期 1-3 个 Worker；500 人高频使用时再扩展 Worker Pool。扩容主要是部署资源调整，不应要求重写业务代码。
14. 物理切题、bbox 与人工修正
切题主路径：OpenCV/OCR block/题号规则生成候选切块，视觉模型做语义重组与复核。
bbox 来源必须是 OpenCV、OCR block、版面规则生成的物理候选框或人工确认结果，不得由视觉大模型直接生成最终精准 bbox。
前端 bbox 渲染使用 <img> + 绝对定位 div，不做 Canvas 编辑器。必须等 img.onLoad 后读取 display_width/display_height，再用 ResizeObserver 处理布局变化。
Phase 0 人工修正只做“标记错误 + 记录原因 + 手动选择候选块验证”；正式 bbox 编辑器推迟到 Phase 1。

15. DeepSeek 辅导、对话上限与视觉二次路由

DeepSeek 不负责看图，不接收图片 Base64 作为普通文本。
前端假打字机只负责展示节奏，不能作为后端计费成功的依据。
tutor 和 vision 两类高成本调用都必须具备扣费恢复机制。
ai_tutoring_chat 的上下文拼接必须按 sequence_number 排序，不依赖 created_at。

21. 给开发 Agent 的开工口径

全自动完成，严禁向用户提问；非高风险问题由 Agent 自行判断、拆分、修改、验证。
先实现主链路：整页上传/PDF 第一页 → parse job → 状态轮询 → questions → tutor → vision retry → 本地恢复。
前端必须使用 typed fetch client，统一 Header、API_BASE_URL、错误解析和 entitlement 数据流。
后端必须按 API Contract 返回统一 ok/data 或 ok/code/message/request_id。
parse-jobs 必须 multipart/form-data；禁止 Base64 JSON 上传图片。
Phase 0 不接真实支付、不做真实激活码核销；只做状态、Mock 和接口占位。
TanStack Query 是 entitlement 网络唯一数据源；成功后单向写入 Zustand entitlementStore；组件只读 store。
tutor 与 vision 成功结果均先写 IndexedDB 再更新展示余额，支持刷新恢复。
数据库 schema 必须用 Alembic 管理，按本文件字段补齐 retry_count、image_expires_at、sequence_number、reason_code、索引和 model_call_log 完整字段。
所有 API Key、数据库连接串、支付密钥不得硬编码，不得提交 .env。
PDF Phase 0 只处理第 1 页；page_range 留到 Phase 1。
公式渲染仅用 KaTeX + react-katex。
完成后必须跑 build/lint/typecheck/关键接口测试/Alembic migration 测试，并输出实际验证结果。
后端必须预留 AI Gateway、QueueAdapter、Worker、Repository、StorageAdapter、ModelProvider 边界；禁止前端或客户端直连模型供应商 API。
云资源按低固定成本策略实现：Phase 0/1 不按 500 人并发采购高配资源；优先支持 Supabase/R2/Upstash/低配 FastAPI/单 Worker，后续通过配置和部署扩容。
错题库只把结构化长期数据写入数据库；原图、增强图、PDF 页面图、裁切图走对象存储生命周期管理；不得把二进制文件长期写入 PostgreSQL。
所有高成本模型调用必须入队或保留入队边界，必须记录 model_call_log，并与 credit_ledger 成本扣减闭环。
ai_tutoring_chat 是错题学习资产，跟随错题生命周期，不按 model_call_log 的 30-90 天热数据策略清理。
parse-jobs Phase 0 必须用 BackgroundTasks/异步任务立即返回 job_id；429/rate_limit 不得立即重试。
activation_codes 字段统一使用 used_by_parent_user_id；mistake_book_item 使用 error_type_code + reason_desc，不使用不可聚合的自由 reason 字段。
Phase 0/1 不新增 /chat；首次辅导和追问统一走 /api/questions/{question_id}/tutor，使用 mode=initial/followup 区分。
